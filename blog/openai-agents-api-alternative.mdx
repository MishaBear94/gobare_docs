OpenAI's [Agents API](https://developers.openai.com/api/docs/guides/agents-api/overview)
went into public beta on 10 September 2026: a hosted Codex harness, a sandbox
per session, artifacts that outlive the machine. If you build on OpenAI models
and nothing below bothers you, use it.

This page is for the other case. You want that shape — send a task over HTTP,
an agent works on a real machine until it's done, you read the results — but
you need a different model, your own key, your own infrastructure, or terms the
beta doesn't offer.

**The short answer:**

| If you want to… | Look at |
|---|---|
| Keep the official `openai` package and change only the endpoint | Rebyte, Open Managed Agents |
| A hosted runtime that runs any model on your own key | Gobare |
| Bring your own harness (Codex CLI, OpenCode) to managed microVMs | DigitalOcean Managed Agents |
| A hosted runtime and you're committed to one lab's models | Claude Managed Agents, Mistral Agents API |
| Run it all on your own infrastructure | Open Managed Agents, AstraBox |
| Deploy your own agent code, any framework, on managed infra | Amazon Bedrock AgentCore |
| Own the loop entirely | OpenAI Agents SDK plus a sandbox provider |

Disclosure: we build [Gobare](https://gobare.dev), one of the options below.
Every claim about another product is quoted or paraphrased from its own public
documentation, checked on 28 September 2026, and there is a section on where we
lose.

## First: the Agents API is not the Agents SDK

The names are close and the products are opposite answers to one question: who
runs the agent loop?

- **The Agents SDK** is open source and runs in your process. You own the loop.
  It can use other providers through LiteLLM and Any-LLM adapters.
- **The Agents API** is hosted. In OpenAI's words, "OpenAI runs the agent
  harness. Your application sends it work and receives results."

So "can I use Claude with OpenAI's agents?" has two answers. With the SDK, yes.
With the hosted API, OpenAI's documentation shows OpenAI models only — every
example uses `gpt-6-astra`, and we could not find a documented way to run a
non-OpenAI model on the hosted path.

Most "Agents SDK alternatives" lists compare frameworks: LangGraph, CrewAI,
LlamaIndex. Those replace the SDK. This page is about replacing the hosted API,
which means something has to run the loop and the machine for you.

## Why teams look for an alternative

Five reasons come up, and each one is on OpenAI's own pages:

1. **Model choice.** The hosted API is built around OpenAI models. If your
   product runs best on Claude, or you route by cost to Kimi or DeepSeek, the
   hosted path is not where that happens.
2. **Data terms.** "The Agents API currently supports data residency only in the
   United States and does not support Zero Data Retention (ZDR)." Choosing a
   self-hosted sandbox "does not make the Agents API ZDR-eligible."
3. **One bill, one vendor.** "Model usage is billed at the selected model's API
   rates … OpenAI-hosted sandboxes use standard container rates." Tokens and
   compute both go to OpenAI. The numbers are in
   [OpenAI Agents API pricing](https://gobare.dev/blog/openai-agents-api-pricing).
4. **Idle lifetime.** "If activity and keep-alives stop for an hour, the sandbox
   can be deleted." Files under `/workspace/outputs` survive as artifacts;
   everything else in the workspace does not.
5. **Beta churn.** Every request carries `OpenAI-Beta: agents=v1`. Names and
   behaviour can move before general availability.

None of these make the Agents API wrong. They make it a specific choice.

## The alternatives, by what you want to keep

### Keep the OpenAI SDK, change the endpoint

**Rebyte** describes itself as a managed agent runtime with durable sessions
and tools, and its docs say to "call the Agents API with the official openai
package, your Rebyte API key and the Rebyte endpoint." If your code already
targets the Agents API and you want the smallest possible diff, this is the
shortest path. Its docs don't cover bring-your-own-key or pricing.

**Open Managed Agents** is an "open-source, self-hosted alternative to Claude
Managed Agents and OpenAI Agents API" under Apache 2.0. It serves both APIs —
Anthropic's `/v1/agents` and `/v1/sessions`, and OpenAI's under `/openai/v1` —
with your own model keys, on Node.js, Docker or Cloudflare Workers, or hosted at
openma.dev. Sandboxes include E2B, Daytona and Cloudflare Containers.

### A hosted runtime on any model, with your own key

**Gobare** runs the agent and its machine; you connect a key from Anthropic,
OpenAI, xAI, OpenRouter, MiniMax, DeepSeek, Qwen, Kimi, GLM or any compatible
endpoint, and every session uses it. The key is verified on save and never
enters a sandbox. Each session is its own sandboxed computer with a shell,
files and a browser, running the open-source [pi](https://github.com/earendil-works/pi)
harness unmodified. It is conceptually aligned with the Agents API and
deliberately not wire-compatible — the request shape is close, the SDK is not
the same.

**DigitalOcean Managed Agents**, in public preview since 22 September 2026, lets
teams "deploy their preferred agent harness (like OpenCode, Codex CLI) or bring
their own." Each session runs in a dedicated Firecracker microVM, billed per
second of active CPU. The model is whatever your harness is configured to call.

### A hosted runtime from one model lab

**Claude Managed Agents** is the same idea as OpenAI's, with Anthropic on the
other side: Anthropic runs the loop, tools execute in Anthropic-managed
sandboxes, and a self-hosted sandbox option moves tool execution onto your
infrastructure. Pick it if you're committed to Claude. We compare it in detail in
[Claude Managed Agents alternative](https://gobare.dev/blog/claude-managed-agents-alternative).

**Mistral Agents API** gives agents built-in tools including a code interpreter
that runs code "in an isolated container", plus web search, image generation
and a document library, and MCP servers as connectors. It runs Mistral models,
and the Agents and Conversations endpoints are marked beta.

### Everything on your own infrastructure

**Open Managed Agents**, above, is the most complete self-hosted option if you
want an API shape your code already knows.

**AstraBox** is an Apache 2.0 project that runs Claude Code, Codex, Hermes,
DeepSeek Harness and pi "as managed Agents on your own infrastructure", on one
Docker host or a Kubernetes cluster, with a bundled LiteLLM gateway for any
Anthropic- or OpenAI-compatible model. It is young.

### Your own agent code, managed infrastructure

**Amazon Bedrock AgentCore** is for teams that already have an agent: "Start
with LangChain, OpenAI Agents SDK, Claude Agent SDK, Strands SDK, or your own
framework, and deploy with any model." You bring the loop; AWS runs it.

**The OpenAI Agents SDK plus a sandbox provider** — E2B, Modal, Daytona and
others — is the most flexible and the most work. You get every model and every
sandbox, and you also own the queue, the retries, the lifecycle, the event
stream and the webhook delivery. The sandbox is the layer underneath; the loop
and everything around it is yours.

### All of them in one table

| | Who runs the loop | Models | OpenAI SDK works unchanged | Open source |
|---|---|---|---|---|
| OpenAI Agents API | OpenAI | OpenAI | Yes | No |
| Rebyte | Rebyte | Not documented | Yes | No |
| Open Managed Agents | You, or openma.dev | Any, your keys | Yes | Yes |
| Gobare | Gobare | Any, your key | No | Harness only (pi) |
| DigitalOcean Managed Agents | Your harness, on DigitalOcean | Your harness's | No | No |
| Claude Managed Agents | Anthropic | Claude | No | No |
| Mistral Agents API | Mistral | Mistral | No | No |
| AstraBox | You | Any, via LiteLLM | No | Yes |
| Bedrock AgentCore | Your code, on AWS | Any | Your code | No |
| Agents SDK + sandbox | You | Any, via adapters | It is the SDK | Yes |

## The same request, side by side

OpenAI's quickstart creates a session like this:

```bash
curl https://api.openai.com/v1/agents/sessions \
  -H "OpenAI-Beta: agents=v1" \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "agent": {
      "model": "gpt-6-astra",
      "instructions": "Write clean code, run it, and report the actual output."
    },
    "environment": { "type": "openai_hosted" },
    "input": "Create tree.py, a script that prints the files in the current directory. Run it.",
    "stream": true
  }'
```

On Gobare, connect a key once, then create the session:

```bash
# Once per organization. The key is verified on save and never enters a sandbox.
curl -X POST https://api.gobare.dev/v1/model-credentials \
  -H "Authorization: Bearer $GOBARE_TOKEN" \
  -H "content-type: application/json" \
  -d '{"key":"sk-ant-..."}'

curl -X POST https://api.gobare.dev/v1/sessions \
  -H "Authorization: Bearer $GOBARE_TOKEN" \
  -H "content-type: application/json" \
  -d '{
    "agent": {
      "model": "claude-sonnet-4-6",
      "instructions": "Write clean code, run it, and report the actual output."
    },
    "input": "Create tree.py, a script that prints the files in the current directory. Run it."
  }'
```

`agent.model`, `agent.instructions` and `input` mean the same thing in both. The
differences are deliberate: there is no beta header, no environment type because
every session gets a Gobare sandbox, and no `stream` flag because events come
from their own endpoint or a webhook.

## Moving over: what maps to what

| OpenAI Agents API | Gobare |
|---|---|
| `POST /v1/agents/sessions` | `POST /v1/sessions` |
| `agent.model`, `agent.instructions`, `input` | Same fields |
| Streamed response on create | `GET /v1/sessions/{id}/events` (SSE, resumable with `Last-Event-ID`), or signed webhooks |
| `/workspace/outputs` becomes artifacts | Same path, same rule |
| Keep-alives; deletable after an hour idle | Paused after 5 idle minutes and woken by the next input; reclaimed two hours after creation |
| Vault credentials keep secrets out of the sandbox | The model key never enters the sandbox; other secrets are injected as environment variables |
| Subagents inside a session | No subagents; your service runs several sessions as a crew |
| Function tools | Function tools, plus approvals and questions a person or your code can answer |
| Model tokens and containers billed by OpenAI | Tokens billed by your provider; sandbox compute is ours |

The full list of intentional differences is in
[Design decisions](https://docs.gobare.dev/design-decisions).

## Where Gobare loses

The part worth reading before you switch.

- **Not wire-compatible.** If you want to keep the `openai` package and change
  only a URL, Rebyte or Open Managed Agents is a smaller move.
- **A workspace has a two-hour ceiling.** A sandbox is reclaimed two hours after
  it was created, paused time included, and a turn still running then ends as
  failed. The workspace is snapshotted first and the next input starts a fresh
  sandbox from it; sessions with a published address or an open SSH connection
  are exempt.
- **One sandbox provider, no bring-your-own-compute.** OpenAI lets you point the
  runtime at your own machines or a partner. We don't.
- **Secrets other than the model key live in the sandbox.** OpenAI's vault
  credentials keep real values outside it. Ours do not, for anything except the
  model key.
- **No subagents.** If you want the agent itself to spawn helpers, OpenAI has it
  and we do not.
- **Concurrency is capped.** 25 sessions per organization by default, raised by
  asking. A session holds its slot until you delete it.
- **Not a ZDR service either.** We store the transcript, because the transcript
  is part of what you are paying for.
- **Pricing is not published yet.** Free while in alpha, with no margin on
  tokens. The rate for compute is not set.

## How to decide

1. **Does it have to be an OpenAI model?** Use OpenAI's Agents API.
2. **Is your code already written against the Agents API?** Rebyte or Open
   Managed Agents keeps the diff to a URL.
3. **Must it run on your own infrastructure?** Open Managed Agents or AstraBox.
4. **Do you already have an agent and just need somewhere to run it?** Bedrock
   AgentCore, or DigitalOcean Managed Agents if it's a CLI harness.
5. **Do you want to own the loop?** The Agents SDK with a sandbox provider.
6. **None of the above — you want a hosted session on your own key, any
   model?** That is what Gobare is for.

## Frequently asked questions

### Can I use Claude with the OpenAI Agents API?

Not on the hosted path, as far as OpenAI's documentation shows: every example
uses an OpenAI model, and there is no documented way to select another
provider. The open-source Agents SDK can use Claude through its LiteLLM or
Any-LLM adapters, but then you run the loop yourself.

### Is there an open-source alternative to the OpenAI Agents API?

Yes. Open Managed Agents implements the Agents API surface under `/openai/v1`
and is Apache 2.0. AstraBox is Apache 2.0 too but exposes its own API.

### Is there a drop-in, OpenAI-compatible endpoint?

Rebyte documents using the official `openai` package against its own endpoint,
and Open Managed Agents serves the same surface. Gobare is deliberately not
wire-compatible.

### Does the OpenAI Agents API support EU data residency or ZDR?

Not during the beta: OpenAI states it supports data residency only in the
United States and does not support Zero Data Retention, including with a
self-hosted sandbox.

### What is the difference between the Agents API and the Agents SDK?

The SDK is a library that runs the agent loop in your process. The API is a
hosted service where OpenAI runs the loop and, optionally, the sandbox. See the
first section above.
